# SQL-01_create_lol_bayes_matchup_training

## Source SQL File
01_create_lol_bayes_matchup_training.sql

## Purpose
Creates the physical SQL table used to store Bayesian matchup training rows.

In plain English:
This table is designed to hold one row per team per historical series, including lane-level team stats, opponent lane stats, team-minus-opponent edges, and bucket fields that can later be used for Bayesian grouping.

This table is meant to support:
- prior win rate
- similar matchup win rate
- Bayesian-smoothed win probability
- future result path probabilities such as 2-0, 2-1, 1-2, 0-2

## SQL Object Created
Creates:

dbo.lol_bayes_matchup_training

This is a physical table, not a view.

## Data It Consumes
This SQL file does not consume data directly.

It only:
1. Drops the table if it already exists.
2. Creates the table.
3. Creates indexes.

A separate population script or SQL process is required to insert data into this table.

## Data It Creates / Updates

### Creates Table
dbo.lol_bayes_matchup_training

### Drops Existing Table
If the table exists, it runs:

DROP TABLE dbo.lol_bayes_matchup_training

That means all existing training data is removed when this file is run.

## Grain
The intended grain is:

one row per team per historical series

Unique index:

series_id + teamname

So each historical series should have one row for each team.

Example:
- BLG vs TES series
  - BLG row
  - TES row

## What Uses This Data
This table is intended to be used by Bayesian matchup logic.

Potential downstream usage:
- Bayesian matchup read
- team-vs-team historical comparison
- similar matchup win probability
- result path probability modeling
- Team Overview Bayesian tab
- lineup scenario recommendations

However, in the current documented app files, the more active Bayes flow appears to use views such as:
- dbo.vw_lol_bayes_matchup_training
- dbo.vw_lol_bayes_strength_matchups
- dbo.vw_lol_bayes_league_priors

So this table may be an earlier or alternate Bayes-training design unless another population script fills it.

## Health Checks

Check table exists:
SELECT
    OBJECT_ID('dbo.lol_bayes_matchup_training', 'U') AS object_id;

Check row count:
SELECT
    COUNT(*) AS rows_count
FROM dbo.lol_bayes_matchup_training;

Check row count by league/season:
SELECT
    league,
    season,
    COUNT(*) AS rows_count,
    COUNT(DISTINCT series_id) AS series_count,
    MIN(series_date) AS first_series_date,
    MAX(series_date) AS last_series_date
FROM dbo.lol_bayes_matchup_training
GROUP BY league, season
ORDER BY season DESC, league;

Check duplicate series/team risk:
SELECT
    series_id,
    teamname,
    COUNT(*) AS rows_count
FROM dbo.lol_bayes_matchup_training
GROUP BY series_id, teamname
HAVING COUNT(*) > 1;

## Important Risk Areas

### Risk 1: Drops existing table
This file drops dbo.lol_bayes_matchup_training if it exists. Running it will erase any populated training rows.

### Risk 2: Creates structure only
This is not a full model-building file. It does not insert any rows.

### Risk 3: May be superseded by newer Bayes views
The current Team Overview app appears to use Bayes strength views. Confirm whether this table is still part of the active workflow.

### Risk 4: Bucket fields are nullable
If the population logic does not fill bucket fields, similar-matchup grouping will be weak.

### Risk 5: Death edge interpretation
Death edges may need careful interpretation because lower deaths are better, while positive death_diff might mean more deaths.
